### Note on the chain-hint join (not a defect)

`_chain_hint(sid)` is called on **every** offer-producing code path (`getaway`, `intent_skip`, the main `offer` branch, embed/qdrant fallback), but the `hint` field is only **recorded in the ledger** on the full `offer`-band call (`enforcer.py:1953`). That means the same hint text can be re-injected on a later turn without a matching ledger row. A strict "stop at the next offer" join (correct for the turn-scoped `offered` ranking and for `route`) therefore *undercounts* hint compliance — checking for a successor take anywhere later in the session is the methodologically correct join for this one signal, and it reproduces the report's 8/16 exactly. I flagged this only to explain why I did not also treat it as a join-boundary defect.

## Defects found (most severe first)

1. **F5 — "successful" latency percentiles include the failed/capped rows.** The report's "Successful queries: p50 43 ms, p90 100 ms" and "Successful embeds: p50 154 ms, p90 277 ms, p99 364 ms" are reproduced *only* when the 53 `qdrant_down` rows (pinned 101-106 ms) and 21 `embed_timeout` rows (pinned 359-381 ms) are left **in** the population used to compute "successful" latency. Excluding them (the population the label actually describes) gives qdrant p50 **38 ms** / p90 **87 ms**, and embed p50 **151 ms** / p90 **257 ms** / p99 **338 ms** — all lower than stated. This weakens (but does not reverse) the "the cap sits at the p90 of normal latency" argument: the real margin is 87 ms vs a 100 ms cap, still tight, but the report's own circular framing (the cap "sits at" a p90 that is partly built from rows *stopped by* the cap) overstates how close it is. R3's core evidence — every down/timeout row landing exactly at its respective cap — is unaffected and remains solid.

2. **F2 — per-harness offered-turn conversion is inflated by a join-boundary bug.** `ledger_deep2.py`'s per-harness conversion loop (`nxt = rs[i+1:i+6]`, a fixed 5-event lookahead) does not stop at the next `offer` event, so it can credit a take to an offer that isn't the one the agent actually responded to. Corrected (stop at the next offer, matching the join `ledger_deep.py`'s own hit@k logic uses): **claude 15/148 (10%)**, not the stated 18/148 (12%). `omp 9/22 (41%)`, `codex 0/9`, `zcode 0/2` are unaffected (no intervening offer inside the 5-event window in those sessions). This is the exact class of bug the review brief warned about; it bit one specific cited figure in F2.

3. **F6 — multi-intent denominator is off by one.** Report states "Multi-intent (ADR-0041) ≥2 takes: 0/143". Reproducing the report's own exact window gives 142 (`581 total decisions − 439 single/no-offer = 142`; directly counting rows with `n_intents` present in `[start, 23:26:30]` also gives 142). An unbounded rerun minutes later picks up a 143rd row, which is almost certainly what produced the stated figure — a live-ledger-growth artifact between sequential queries at write time, not a logic error. Correct figure: **0/142**. The `3/439` single-intent-control figure is exact either way.

4. **F10 — the fallback-rate explanation, and R6's proposed fix, omit the `negation` band.** `analyze.py`'s `fb` counter (line 596) sums any row with a truthy `fallback` field. That field is truthy on `intent_skip` rows (`"conversational"`, 147 rows), on real-outage `fallback`-band rows (74 rows), **and** on `negation`-band rows (`"skill_refusal"`, `enforcer.py:1821`, 6 rows). `147 + 74 + 6 = 227` matches the report's own cited numerator exactly, but the prose only names the first two components ("147 intent_skip... together with the 74 real timeouts" = 221, not 227). R6's mechanism ("count `fallback` only where the value is `embed_timeout`/`embed_down`/`qdrant_down`; print `intent_skip` separately") would still leave the negation rows contaminating the "fixed" line. Low severity — the cited number (227/582, 39%) and the "true share 13%" conclusion are both correct — but the causal explanation is incomplete and the recommendation would ship with the same latent bug.

5. **Minor citation off-by-one.** F3 cites the P5 keep-off drop at `hooks/scripts/enforcer.py:1871`; the actual line is `1872` (`cands, _dropped = _drop_keepoff(cands, KEEPOFF)`). Cosmetic.

6. **Two figures I could not reproduce — flagged UNVERIFIABLE, not wrong.**
   - F2: "The ledger sees only Skill-tool invocations (**61 turns**)." I tried several plausible definitions — ledger `auto`+`manual` takes restricted to claude-harness sessions (94/95), total Skill-tool `tool_use` blocks across all in-window turns in the 42 transcripts (82), Skill-tool-bearing **human** turns (55), and total Skill-tool calls within human turns (67) — none produced 61. The broader claim this number supports ("ledger uptake undercounts real usage by ~4×") is independently confirmed: `analyze.py`'s live "uptake: 91/630 14%" against trail2's human-prompt USING rate of 110/195 = 56% gives 56/14 = 4.0×, exactly the cited factor, via a different and fully reproducible path.
   - F1: "Cost per injected preview ≈ 2,021 chars (~500 tokens), measured from 82 preview-bearing `UserPromptSubmit` attachments." No surviving script computes this, and the raw hook `additionalContext` payload sizes aren't cheaply isolable from the transcript JSONL without reconstructing the exact 82-file sample the author used. Not disputed, just not independently re-derived.
